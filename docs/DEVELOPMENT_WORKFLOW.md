# Workflow разработки и выпуска

Этот документ — единственный источник процесса разработки, агентских ролей,
ревью, публикации, merge и permission boundaries. Для исследования и других
read-only задач применяются только релевантные этапы; отсутствие изменений не
требует release-процесса.

По явному запросу пользователя на облегчённый режим вместо полного процесса
применяется сокращённый маршрут из раздела 2.1. Такой запрос действует только
для текущей задачи и не является постоянной настройкой репозитория.

## 0. Task Contract

До передачи первой роли главный агент копирует
`.codex/task.example.toml` в `.codex/work/<feature-slug>/task.toml`. Manifest
хранит только:

- slug, текущую `scope_revision` и текущий status;
- один `requirements_source`, BR/AC IDs, task `allowed_files`, non-goals и
  `done_when`;
- партии: ID, не более двух пунктов, BR/AC IDs, `allowed_files` и
  прямые dependencies.

Полный текст каждого BR/AC имеет одного владельца: approved
`business.md` для продуктовой задачи или короткий `scope.md` для технической.
Остальные материалы ссылаются на IDs и не копируют требования.

Каталог `.codex/work/` игнорируется Git и хранит только короткие текущие
материалы, без production-кода, diff, полных логов и архива ревизий.
`make agent-work-check` — обычный coordination guardrail, а не security
boundary. Он проверяет форму manifest, branch/slug, текущий status,
границы партий и текущие и закоммиченные изменения ветки против
task `allowed_files`.

Изменение поведения, контракта, компонента или non-goal требует
подтверждения пользователя, повышения `scope_revision` и новых packets.
Риски и рекомендации сами по себе требованиями не становятся.

## 1. Владение документацией

Перед добавлением продуктовой или технической информации выбери ровно один
документ-владелец:

| Информация | Владелец | Остальные документы |
|------------|----------|----------------------|
| Пользовательские сценарии, тарифы и бизнес-правила | [BUSINESS.md](BUSINESS.md) | Только ссылка или краткий контекст |
| Стабильные границы компонентов, потоки и инфраструктура | [ARCHITECTURE.md](ARCHITECTURE.md) | Не повторять алгоритмы фич |
| HTTP/VDS методы, payload, status и wire-errors | [CONTRACTS.md](CONTRACTS.md) | Не копировать JSON и endpoint-спеки |
| Поля хранения, связи, constraints и DB-инварианты | [MODELS.md](MODELS.md) | Не пересказывать бизнес-flow |
| Ответственность приложения и карта модулей | [docs/apps/](apps/) | Только четыре канонических раздела и ссылки |
| Разработка, роли, ревью, PR и разрешения | Этот документ | `AGENTS.md` только маршрутизирует |
| Release-команды, rollback и production smoke | [DEPLOY.md](DEPLOY.md) | Не копировать исполняемые команды |

Файлы `docs/apps/*.md` используют только разделы `Зона ответственности`,
`Карта компонентов`, `Зависимости`, `Границы`. Они называют модели, сервисы и
задачи, но не дублируют бизнес-правила, HTTP payload или алгоритмы.

Перед публикацией обязательно запусти:

```bash
make docs-check
```

Проверка блокирует release-команды и HTTP-спеки вне владельца, workflow-механику
в routing-документах, произвольные feature-разделы в app maps, длинные
дублированные абзацы/code blocks, отсутствующие канонические ссылки и битые
локальные Markdown-ссылки. Если уникальная информация нужна в двух местах,
оставь полный текст у владельца, а во втором месте — ссылку и только необходимый
контекст.

## 2. Маршрут задачи

Главный агент выбирает минимальный маршрут из ролей `.codex/agents/`:

- документация и техническое обслуживание без изменения поведения — главный
  агент, TDD для нового executable tooling, один независимый reviewer;
- небольшая локальная продуктовая фича — `product-agent`, облегчённый
  `plan-maker`, `plan-implementer`, batch `code-reviewer`, `product-reviewer`;
- обычная фича — дополнительно `product-architect` и архитектурное ревью плана;
- крупная фича — несколько независимых партий implementer/reviewer.

Архитектор не нужен, если не меняются контракты, модели, взаимодействия
компонентов или существенные нефункциональные требования. Один
`plan-implementer` получает не более двух пунктов; параллельные партии не должны
иметь незавершённых зависимостей или пересекающихся файлов.

Каждая роль получает один короткий packet: режим, `scope_revision`,
назначенные пункты, BR/AC IDs, `allowed_files`, dependencies, non-goals,
`done_when` и ссылки только на нужные рабочие материалы. До планирования
назначенных пунктов и dependencies ещё нет. Полные requirements и plan
в packet не копируются; только оркестратор читает полный `task.toml`.
Выход за границы возвращается как `scope_change_request`, без изменений.

### 2.1. Облегчённый режим по запросу пользователя

Облегчённый режим включается только прямой командой пользователя для текущей
задачи, например: «работай в облегчённом режиме». В этом режиме главный агент:

1. Самостоятельно исследует задачу, принимает технические решения, реализует
   изменение и исправляет найденные проблемы.
2. Не создаёт Task Contract и материалы `.codex/work/`, requirements,
   спецификации архитектуры, планы или acceptance-документы. Роли
   `product-agent`, `product-architect`, `plan-maker`, `plan-implementer` и
   `product-reviewer`, а также batch review не используются.
3. Сам выбирает релевантные тесты и технические проверки пропорционально риску
   изменения, соблюдая правила реализации из `AGENTS.md`.
4. Работает в feature-ветке, коммитит результат, публикует Pull Request в
   `main` и передаёт финальный diff независимому read-only `code-reviewer`.
   Контекстом ревью служат исходный запрос пользователя, описание PR, проверки
   и ожидаемый head SHA; BR/AC IDs и `scope_revision` не требуются.
5. При `VERDICT: changes_requested` самостоятельно исправляет замечания в
   пределах запроса и передаёт новый head SHA новому `code-reviewer`. После
   `VERDICT: approved` останавливается и запрашивает разрешение пользователя на
   merge.
6. После разрешения мержит только одобренный head SHA. Затем выполняет
   подготовительные действия из раздела «Новый релиз» в `DEPLOY.md`,
   останавливается и отдельно запрашивает разрешение на production deploy.

Прямой запрос на облегчённый режим не является разрешением на merge или deploy.
Эти две permission boundaries из раздела 7 сохраняются без изменений. Любые
действия вне текущей задачи также требуют отдельного запроса пользователя.

## 3. Подготовка

1. Прочитай постановку, `AGENTS.md` и только релевантные документы-владельцы.
2. Проверь `git status --short`, текущую ветку и незавершённые изменения.
3. Обнови локальный `main` без переписывания истории и создай непосредственно
   в текущем checkout ветку `codex/<feature-slug>`. Worktree запрещён.
4. Проверь `gh auth status`; отсутствие CLI или авторизации блокирует PR и не
   разрешает прямой push в `main`.
5. Найди существующие сервисы, selectors, DTO, exceptions, factories и тестовые
   паттерны, которые можно переиспользовать.
6. Для рискованных изменений заранее определи совместимость миграций и rollback.

Чужие изменения сохраняй. Если рабочее дерево грязное или `main` разошёлся с
`origin/main`, сначала исследуй состояние и не применяй destructive git-команды.

## 4. Реализация через TDD

Для каждого нового поведения:

1. Напиши минимальный тест.
2. Запусти его и получи ожидаемый RED.
3. Внеси минимальное production-изменение.
4. Получи GREEN и только затем рефактори.
5. Сверь diff с Task Contract и владением файлов.

Следуй service layer, DI, selectors, DTO и другим правилам `AGENTS.md`. Не
рефактори соседний код «заодно». Документацию обновляй только у владельца из
раздела 1.

## 5. Проверка

Запусти релевантные тесты, затем обязательные repository gates:

```bash
make agent-work-check
make test
cd bot && uv run pytest
cd .. && make docs-check
docker compose -f docker-compose.yml config --quiet
git diff --check
```

Дополнительно проверь миграции и доступные статические проверки, если diff их
затрагивает. Просмотри итоговый diff на секреты, unrelated changes и временные
артефакты `.codex/work/`, `docs/features/`, `docs/superpowers/` или
`superpowers/`.

## 6. Pull Request и ревью

1. Формирует компактный Review Brief: `scope_revision`, BR/AC IDs, цель,
   наблюдаемое поведение, non-goals, критерии, проверки, риски и deploy impact.
2. Коммитит только относящиеся к задаче файлы в feature-ветке.
3. Пушит ветку и открывает Pull Request в `main`; прямой push в `main` запрещён.
4. Фиксирует URL, номер PR и точный head SHA.
5. Передаёт новому `code-reviewer` Review Brief, PR и ожидаемый SHA.

Публикация и фиксация проверяемого SHA выполняются явно:

```bash
FEATURE_BRANCH="$(git branch --show-current)"
PR_BODY_FILE="<prepared-review-brief>"
PR_URL="$(gh pr create --base main --head "$FEATURE_BRANCH" \
  --title "<title>" --body-file "$PR_BODY_FILE")"
PR_NUMBER="$(gh pr view "$PR_URL" --json number --jq '.number')"
PR_HEAD_SHA="$(gh pr view "$PR_NUMBER" --json headRefOid --jq '.headRefOid')"
test "$PR_HEAD_SHA" = "$(git rev-parse HEAD)"
gh pr checks "$PR_NUMBER" --watch
```

Финальный reviewer работает read-only, читает канонические документы, полный
diff и checks, затем публикует один `gh pr review --comment`. Временные файлы
`.codex/work/` он не читает и собственные замечания не исправляет. До запуска
reviewer все write-сессии должны завершиться; оркестратор не меняет checkout до
окончания ревью и сравнивает `git status` и diff до и после.

Каждая находка имеет один тип:

- `blocking_in_scope` — нарушение Task Contract, Review Brief, non-goal,
  repository gate или регрессия из diff;
- `scope_change_request` — новое поведение, компонент или обязательный hardening;
- `follow_up` — необязательное улучшение.

`VERDICT: changes_requested` допустим только при `blocking_in_scope`; иначе
используется `VERDICT: approved`. Падение `make docs-check` или новое смысловое
дублирование информации между документами считается `blocking_in_scope` для
задачи, меняющей документацию. После fix commit старый review устаревает, и
новый reviewer проверяет новый head SHA.

Перед передачей пользователю главный агент подтверждает зелёные checks,
неизменный SHA и последний `VERDICT: approved`, после чего оставляет PR открытым
до отдельного разрешения пользователя на merge.

## 7. Merge и deploy boundary

Только после явного разрешения пользователя агент мержит проверенный head SHA в
`main` и сверяет опубликованный merge commit с `origin/main`. Разрешение на
разработку или PR не считается разрешением на merge.

```bash
gh pr merge "$PR_NUMBER" --squash --delete-branch \
  --match-head-commit "$PR_HEAD_SHA"
```

После успешного merge или явного закрытия PR удали
`.codex/work/<feature-slug>/`; долговечная история остаётся в PR и
канонической документации.

После merge следуй разделу [«Новый релиз» в DEPLOY.md](DEPLOY.md#новый-релиз)
для syntax-check и подготовки точного `RELEASE_SHA`. Затем остановись, назови
SHA, результаты проверок и существенные риски и запроси новое явное разрешение.
Разрешение на merge или предыдущий deploy не разрешает production deploy.

Только после нового ответа пользователя выполняй release и post-deploy по
[DEPLOY.md](DEPLOY.md). Для документационного diff без runtime/config/deploy
impact выпуск production не требуется.
