# Workflow разработки и выпуска

Этот документ — единственный источник процесса разработки, ревью, публикации,
merge и permission boundaries. По умолчанию используется компактный маршрут;
полный Task Contract нужен только для задач с повышенным риском.

Для исследования и других read-only задач применяются только релевантные
этапы. Если файловых изменений нет, PR и release-процесс не требуются.

## 1. Выбор маршрута

### Компактный маршрут по умолчанию

Главный агент самостоятельно исследует задачу, принимает технические решения,
реализует изменение через TDD и выполняет проверки пропорционально риску. Он не
создаёт Task Contract, BR/AC, временные specifications, plans или acceptance-
документы и не запускает продуктовые роли.

После реализации агент публикует Pull Request и передаёт его одному независимому
read-only `code-reviewer`. Контекстом ревью служат исходный запрос, компактный
Review Brief, проверки и точный head SHA.

### Полный маршрут для рискованных задач

Полный маршрут применяется, если задача меняет хотя бы одну из областей:

- платёжные бизнес-правила или движение денег;
- модели, миграции или DB-инварианты;
- внешний HTTP/VDS контракт;
- безопасность, авторизацию или обработку секретов;
- несколько тесно связанных компонентов;
- крупный объём с независимыми партиями реализации.

Пользователь может явно потребовать полный маршрут для любой задачи или,
наоборот, компактный маршрут для конкретной рискованной задачи. Это не даёт
разрешения на merge или deploy.

В полном маршруте главный агент создаёт
`.codex/work/<feature-slug>/task.toml` по `.codex/task.example.toml`. Manifest
хранит `scope_revision`, requirements source, BR/AC IDs, allowed files,
non-goals, done criteria и партии не более чем из двух пунктов. Рабочий каталог
игнорируется Git и удаляется после merge или закрытия PR.

Роли подключаются только когда дают отдельную ценность:

- `product-agent` формализует продуктовые требования;
- `product-architect` нужен для изменения контрактов, моделей или границ;
- `plan-maker` разбивает утверждённый scope на исполнимые партии;
- `plan-implementer` выполняет назначенную партию через TDD;
- `code-reviewer` независимо проверяет batch или финальный PR;
- `product-reviewer` подтверждает BR/AC для продуктовой задачи.

`make agent-work-check` — локальная проверка Task Contract полного режима, а не
общий repository gate и не security boundary.

## 2. Владение документацией

Перед добавлением информации выбери ровно один документ-владелец:

| Информация | Владелец | Остальные документы |
|------------|----------|----------------------|
| Пользовательские сценарии, тарифы и бизнес-правила | [BUSINESS.md](BUSINESS.md) | Только ссылка или краткий контекст |
| Стабильные границы компонентов, потоки и инфраструктура | [ARCHITECTURE.md](ARCHITECTURE.md) | Не повторять алгоритмы фич |
| HTTP/VDS методы, payload, status и wire-errors | [CONTRACTS.md](CONTRACTS.md) | Не копировать JSON и endpoint-спеки |
| Поля хранения, связи, constraints и DB-инварианты | [MODELS.md](MODELS.md) | Не пересказывать бизнес-flow |
| Ответственность приложения и карта модулей | [docs/apps/](apps/) | Только четыре канонических раздела и ссылки |
| Разработка, ревью, PR и разрешения | Этот документ | `AGENTS.md` только маршрутизирует |
| Release-команды, rollback и production smoke | [DEPLOY.md](DEPLOY.md) | Не копировать исполняемые команды |

Файлы `docs/apps/*.md` используют только разделы `Зона ответственности`,
`Карта компонентов`, `Зависимости`, `Границы`. Если информация нужна в двух
местах, полный текст остаётся у владельца, а второе место содержит ссылку.

## 3. Подготовка

1. Прочитай постановку, `AGENTS.md` и только релевантные документы-владельцы.
2. Проверь `git status --short`, текущую ветку и незавершённые изменения.
3. Обнови `main` без переписывания истории и создай в текущем checkout ветку
   `codex/<feature-slug>`. Worktree запрещён.
4. Проверь `gh auth status`; отсутствие CLI или авторизации блокирует PR.
5. Найди существующие сервисы, selectors, DTO, exceptions, factories и тесты,
   которые можно переиспользовать.
6. Для рискованных изменений заранее определи совместимость и rollback.

Чужие изменения сохраняй. Не применяй destructive Git-команды для очистки
грязного дерева или расхождения с `origin/main`.

## 4. Реализация

Для каждого нового поведения или исправления:

1. Напиши минимальный тест.
2. Запусти его и получи ожидаемый RED.
3. Внеси минимальное production-изменение.
4. Получи GREEN и только затем рефактори.
5. Проверь отсутствие unrelated changes.

Для чистого перемещения или разделения кода используй существующие поведенческие
тесты как защиту и не добавляй тесты, проверяющие только расположение текста.
Следуй `AGENTS.md` и не рефактори соседний код «заодно».

## 5. Проверка

Сначала запусти focused tests, затем общие repository gates:

```bash
make lint
make test
cd bot && uv run pytest
cd .. && make docs-check
docker compose -f docker-compose.yml config --quiet
git diff --check
```

В полном режиме дополнительно выполни `make agent-work-check`. Для затронутых
миграций, инфраструктуры или release-файлов добавь соответствующие проверки из
документа-владельца.

Просмотри итоговый diff на секреты, лишние изменения и временные материалы.

## 6. Pull Request и ревью

1. Сформируй Review Brief: цель, наблюдаемое поведение, non-goals, критерии,
   проверки, риски и deploy impact. В полном режиме добавь `scope_revision` и
   BR/AC IDs.
2. Закоммить только относящиеся к задаче файлы.
3. Запушь feature-ветку и создай PR в `main`; прямой push в `main` запрещён.
4. Зафиксируй URL, номер PR и точный head SHA.
5. Дождись зелёных checks и передай PR независимому `code-reviewer`.

```bash
FEATURE_BRANCH="$(git branch --show-current)"
PR_BODY_FILE="<prepared-review-brief>"
PR_URL="$(gh pr create --base main --head "$FEATURE_BRANCH" \
  --title "<title>" --body-file "$PR_BODY_FILE")"
PR_NUMBER="$(gh pr view "$PR_URL" --json number --jq '.number')"
PR_HEAD_SHA="$(gh pr view "$PR_NUMBER" --json headRefOid --jq '.headRefOid')"
test "$PR_HEAD_SHA" = "$(git rev-parse HEAD)"
gh pr checks "$PR_NUMBER" --watch
```

Reviewer работает read-only, сверяет head SHA, Review Brief, полный diff и
checks, затем публикует один `gh pr review --comment`. Он не исправляет свои
находки и не читает `.codex/work/`.

`blocking_in_scope` означает нарушение запроса, Review Brief, утверждённого
Task Contract или regression из diff. Новое поведение вне scope возвращается
как `scope_change_request`, необязательное улучшение — как `follow_up`.
`VERDICT: changes_requested` допустим только при `blocking_in_scope`; иначе
используется `VERDICT: approved`.

После исправления нужен новый review актуального SHA. Одобренный PR остаётся
открытым до отдельного разрешения пользователя на merge.

## 7. Merge и deploy boundary

Только после явного разрешения пользователя агент мержит проверенный head SHA:

```bash
gh pr merge "$PR_NUMBER" --squash --delete-branch \
  --match-head-commit "$PR_HEAD_SHA"
```

После merge следуй разделу [«Новый релиз» в DEPLOY.md](DEPLOY.md#новый-релиз)
для подготовки точного `RELEASE_SHA`. Затем остановись и запроси новое явное
разрешение на production deploy. Разрешение на разработку, PR или merge не
разрешает deploy.

Для документационного diff без runtime/config/deploy impact production release
не требуется.
