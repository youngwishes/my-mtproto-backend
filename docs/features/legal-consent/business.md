# Явное согласие при первом запуске бота

**Статус:** approved

## Проблема

Сейчас первый `/start` сразу передаёт Telegram-данные пользователя в backend,
создаёт `SystemUser` и показывает главное меню. Новый пользователь не подтверждает
пользовательское соглашение и согласие на обработку персональных данных до начала
регистрации.

## Ожидаемая ценность

Новый пользователь явно принимает оба документа до регистрации и начала
использования сервиса. Существующие пользователи продолжают работу без нового
экрана согласия.

## Пользователи

- новый Telegram-пользователь, которого ещё нет в backend;
- существующий `SystemUser`, зарегистрированный до выпуска фичи;
- новый пользователь, пришедший по реферальной ссылке.

## Scope

- read-only проверка существования и статуса согласия при `/start`;
- единый экран согласия для нового пользователя;
- ссылки на действующие страницы `/terms` и `/privacy`;
- одна кнопка явного принятия обоих документов;
- регистрация пользователя только после нажатия кнопки;
- сохранение реферального payload до принятия без server-side записи;
- продолжение обычного `/start` после успешного принятия;
- новый флаг согласия в `SystemUser`;
- значение `true` для всех существующих пользователей при миграции.

## Non-goals

- изменение текстов юридических документов или их URL;
- версионирование согласий, время принятия или повторный запрос после изменения
  документов;
- отзыв ранее данного согласия;
- изменение логирования или телеметрии;
- изменение правил бесплатного периода, оплаты или реферальной программы;
- отдельные согласия или отдельные кнопки для двух документов;
- web UI.

## Сценарии

### Новый пользователь без реферала

1. Пользователь отправляет `/start`.
2. Приложение выполняет только read-only проверку статуса и не создаёт либо не
   обновляет данные пользователя.
3. Бот показывает одним сообщением ссылки на оба документа и кнопку принятия.
4. После нажатия кнопки приложение регистрирует пользователя с принятым
   согласием.
5. То же сообщение заменяется обычным стартовым экраном и главным меню.

### Новый пользователь по реферальной ссылке

Сценарий совпадает с обычной регистрацией, но допустимый referrer переносится из
`/start` в действие кнопки и сохраняется только при успешном принятии.

### Пользователь с сохранённым согласием

Read-only проверка возвращает сохранённое согласие `true`. Бот не показывает
запрос согласия и сразу отображает обычный стартовый экран.

### Повторное принятие

Повторная обработка того же действия не создаёт второго пользователя, не меняет
сохранённого referrer и приводит к обычному стартовому экрану.

### Ошибка

Если проверка статуса или операция принятия завершается ошибкой, бот не
регистрирует пользователя как успешно согласившегося и не открывает главное
меню. Пользователь может безопасно повторить действие. Если согласие уже
сохранено, но редактирование Telegram-сообщения не удалось, повторный `/start`
открывает обычный стартовый экран без повторного согласия.

## Требования

- **BR-001.** Согласие считается единым явным подтверждением пользовательского
  соглашения и согласия на обработку персональных данных.
- **BR-002.** При `/start` разрешена read-only проверка по Telegram ID, которая
  не создаёт и не обновляет `SystemUser`.
- **BR-003.** Новый пользователь до нажатия кнопки не регистрируется, а
  полученные из Telegram данные не записываются в backend.
- **BR-004.** Новый пользователь получает одно сообщение с понятным описанием
  действия, ссылками `/terms` и `/privacy` и одной утвердительной кнопкой.
- **BR-005.** До успешного принятия главное меню новому пользователю не
  показывается.
- **BR-006.** Допустимый реферальный payload переносится в действие кнопки без
  server-side persistence до принятия. Нечисловой payload и self-referral не
  сохраняются.
- **BR-007.** После нажатия кнопки новый `SystemUser` создаётся с флагом
  согласия `true`; значение поля по умолчанию для других новых записей —
  `false`.
- **BR-008.** После успешной регистрации то же сообщение редактируется в
  действующий стартовый экран с корректным предложением бесплатного периода и
  главным меню.
- **BR-009.** Все существующие на момент миграции пользователи получают
  значение флага `true` и не видят новый запрос.
- **BR-010.** Проверка статуса и принятие являются раздельными операциями:
  первая не изменяет состояние, вторая идемпотентно фиксирует согласие.
- **BR-011.** Повторное принятие не создаёт дубликат пользователя и не
  перезаписывает ранее сохранённую реферальную атрибуцию.
- **BR-012.** При ошибке read-only проверки или операции принятия приложение не
  продолжает onboarding как при успешном согласии и позволяет повторить
  попытку. Неуспешная операция принятия не оставляет нового пользователя с
  частично сохранённым состоянием.
- **BR-013.** Ошибка редактирования Telegram-сообщения после успешно
  сохранённого согласия не отменяет согласие; повторный `/start` показывает
  обычный стартовый экран.

## Критерии приёмки

- **AC-001.** Для отсутствующего в backend Telegram ID вызов `/start` не создаёт
  и не изменяет ни одной записи пользователя.
- **AC-002.** Новый пользователь видит одно consent-сообщение, содержащее две
  рабочие ссылки — `/terms` и `/privacy` — и одну кнопку явного принятия.
- **AC-003.** До нажатия кнопки в сообщении нет действий главного меню, а
  `SystemUser` для пользователя отсутствует.
- **AC-004.** После успешного принятия существует ровно один `SystemUser` с
  флагом `true`, а то же Telegram-сообщение содержит обычный стартовый экран и
  главное меню.
- **AC-005.** При `/start <referrer_id>` допустимый referrer не хранится на
  сервере до принятия и сохраняется при успешной регистрации.
- **AC-006.** Нечисловой referrer и Telegram ID самого пользователя не
  сохраняются при регистрации.
- **AC-007.** Повторная обработка accept для уже созданного пользователя
  завершается успешно, не создаёт дубль и не меняет referrer.
- **AC-008.** Ошибка read-only проверки не приводит к созданию пользователя или
  показу главного меню.
- **AC-009.** Ошибка операции принятия не создаёт `SystemUser` и не показывает
  успешный стартовый экран; повторная попытка может завершить регистрацию.
- **AC-010.** После миграции количество существующих пользователей и их
  бизнес-данные не изменены, а новый флаг у каждой существующей записи равен
  `true`.
- **AC-011.** Существующий пользователь после миграции при `/start` не видит
  consent-сообщение и получает прежний стартовый сценарий.
- **AC-012.** Новый пользователь не становится кандидатом на бесплатную выдачу,
  рассылки или реферальную статистику до успешного принятия, поскольку до этого
  запись пользователя отсутствует.
- **AC-013.** Если пользователь создан с флагом `true`, но редактирование
  consent-сообщения завершилось ошибкой, следующий `/start` не запрашивает
  согласие повторно и показывает обычный стартовый экран.

## Ограничения

- пользовательское взаимодействие происходит только в Telegram-боте;
- используются существующие документы `https://mtprotokeys.ru/terms` и
  `https://mtprotokeys.ru/privacy`;
- до принятия допустима только read-only проверка статуса без записи данных;
- реферальный payload переносится без server-side persistence;
- изменение логирования не входит в фичу.

## Риски

- существующие пользователи получают `true` миграцией без нового действия в
  боте; это осознанное продуктовое решение;
- единый boolean не хранит версию документов и время принятия;
- потеря или некорректный перенос referral payload нарушит действующую
  реферальную атрибуцию;
- неидемпотентное принятие может создать дубликат или дать пользователю
  противоречивый результат после повторного нажатия;
- переход к главному меню при ошибке записи создаст ложное подтверждение
  согласия.

## Открытые вопросы

Блокирующих продуктовых вопросов нет. Точная редакция consent-сообщения и подписи
кнопки может быть выбрана при реализации, если она недвусмысленно сообщает о
совместном принятии обоих документов.
