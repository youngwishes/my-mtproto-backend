# Комплаенс пользовательских текстов для эквайринга — продуктовые требования

- **Статус:** approved
- **Scope revision:** 2
- **Основание статуса:** пользователь явно утвердил цель, пользовательский
  сценарий, BR-001–BR-006, AC-001–AC-005 и non-goals Scope Contract revision 2.

## Проблема

В видимых пользователю текстах Telegram-бота и backend-уведомлений присутствуют
формулировки, не соответствующие требованиям менеджера эквайринга, а обращения
за помощью направляются не в актуальную поддержку.

## Ожидаемая ценность

- Пользователь получает нейтральные и соответствующие требованиям эквайринга
  объяснения и уведомления без формулировок про обход ограничений и блокировки.
- Пользователь может обратиться за помощью через единый актуальный контакт
  `@mtprotokeys_support` и точную ссылку на него.
- Приглашения подписаться на новостной канал продолжают вести на
  `@mtproto_keys`.

## Пользователи

- Пользователь Telegram-бота, который читает FAQ, получает рассылку, сообщение
  об ошибке или уведомление либо нажимает кнопку «Поддержка».

## Scope

В изменение входят только видимые пользователю тексты Telegram-бота и
backend-уведомлений, связанные с:

- ответом FAQ;
- broadcast-сообщениями;
- сообщениями об ошибках и уведомлениями с обращением в поддержку;
- кнопкой «Поддержка»;
- сохранённым в БД шаблоном `NotificationTemplate` со slug
  `sorry_server_error`;
- сохранением `@mtproto_keys` в приглашениях подписаться на новостной канал.

## Non-goals

В изменение не входят:

- `README` и `bot/README`;
- внутренняя и историческая техническая документация, кроме обязательного
  feature artifact;
- внешние посты Telegram-канала;
- технические термины о DB/ORM locking;
- изменение тарифов, API или моделей;
- изменение поведения VPN, MTProxy или MTProto;
- проверка доступности username;
- рефакторинг.

## Пользовательские сценарии

### S-001. Чтение FAQ

1. Пользователь открывает соответствующий вопрос FAQ.
2. Пользователь получает точный ответ: «Прокси помогает Telegram работать
   стабильнее и уменьшает потери при плохом интернете, защищает трафик.
   Максимальная скорость зависит от твоего интернета».
3. Текущие подходящие emoji и разметка могут сохраняться, только если они не
   меняют смысл ответа.

### S-002. Получение broadcast, сообщения об ошибке или уведомления

1. Пользователь получает видимое сообщение Telegram-бота или backend.
2. Сообщение не содержит формулировок про обход ограничений и блокировки.
3. Если сообщение призывает обратиться за помощью, оно указывает
   `@mtprotokeys_support`.

### S-003. Переход в поддержку

1. Пользователь нажимает кнопку «Поддержка».
2. Кнопка открывает `https://t.me/mtprotokeys_support`.

### S-004. Приглашение в новостной канал

1. Пользователь получает приглашение подписаться на новостной канал.
2. В таком приглашении сохраняется `@mtproto_keys`.

### S-005. Получение сохранённого сообщения об ошибке сервера

1. Существующий сохранённый в БД шаблон `sorry_server_error` обновляется при
   применении новой data migration.
2. Пользователь, получивший сообщение по этому шаблону после обновления, видит
   новый контакт поддержки.
3. Шаблоны приглашений в новостной канал при этом не изменяются.

## Бизнес-требования

- **BR-001.** Удалить из видимых пользователю сообщений формулировки про обход
  ограничений и блокировки; слова VPN/MTProxy/MTProto разрешены.
- **BR-002.** Точный новый FAQ-ответ: «Прокси помогает Telegram работать
  стабильнее и уменьшает потери при плохом интернете, защищает трафик.
  Максимальная скорость зависит от твоего интернета» (сохранить текущий
  подходящий emoji/разметку, если они не меняют смысл).
- **BR-003.** Все пользовательские обращения за помощью направлять на
  `@mtprotokeys_support`; кнопка ведёт на
  `https://t.me/mtprotokeys_support`.
- **BR-004.** `@mtproto_keys` сохраняется только в пользовательских
  приглашениях подписаться на новостной канал.
- **BR-005.** Существующий сохранённый `NotificationTemplate`
  `sorry_server_error` в БД должен быть обновлён новой data migration.
- **BR-006.** Доступность/существование `@mtprotokeys_support` по сети не
  проверяется и не блокирует тесты, PR или выпуск.

## Критерии приёмки

- **AC-001 (BR-001, BR-002).** FAQ и broadcast не содержат запрещённого
  контекста и используют утверждённые нейтральные формулировки.
- **AC-002 (BR-003).** Кнопка поддержки открывает точный новый URL.
- **AC-003 (BR-003, BR-004).** Все пользовательские сообщения с призывом
  обратиться за поддержкой содержат новый username; новостные упоминания
  остаются прежними.
- **AC-004 (BR-004, BR-005).** Data migration меняет только support contact в
  `sorry_server_error` и не меняет `invite_to_channel`/news templates.
- **AC-005 (BR-006).** Релевантные тесты и полный `make test` зелёные; сетевой
  availability-check отсутствует.

## Ограничения

- Работа ведётся только по неизменяемому `scope_revision: 2`.
- Архитектурное изменение не требуется.
- Точные FAQ-текст, support username и URL должны сохраняться без смысловых
  изменений.
- Слова VPN, MTProxy и MTProto сами по себе не являются запрещёнными.
- Доступность или существование support username по сети не проверяется.
- Изменение ограничено локальной корректировкой пользовательских текстов и
  обновлением существующего сохранённого шаблона через data migration.

## Риски

- Частичное обновление статических и сохранённых в БД сообщений может оставить
  разные контакты поддержки в разных пользовательских сценариях.
- Глобальная замена `@mtproto_keys` может ошибочно изменить приглашения в
  новостной канал, где этот username должен сохраниться.
- Изменение шаблонов помимо `sorry_server_error` может затронуть новостные
  приглашения за пределами утверждённого scope.
