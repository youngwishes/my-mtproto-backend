# AGENTS.md

Инструкции для AI-агентов, работающих с MTPRoto Keys.

## Контекст проекта

MTPRoto Keys — Django backend сервиса подписки на MTProto-прокси. Пользовательское
взаимодействие происходит через Telegram-бота из `bot/`; web UI отсутствует.

Перед изменением соответствующей части системы изучи профильную документацию:

- `docs/BUSINESS.md` — бизнес-правила;
- `docs/ARCHITECTURE.md` — архитектура и инфраструктура;
- `docs/CONTRACTS.md` — API-контракты;
- `docs/MODELS.md` и `docs/apps/` — модели и приложения;
- `docs/DEVELOPMENT_WORKFLOW.md` — обязательный процесс разработки фичи;
- `docs/DEPLOY.md` — production-релиз.

## Обязательный workflow

Разработку новой фичи веди по `docs/DEVELOPMENT_WORKFLOW.md`. Она считается
доставленной на ревью только после реализации, зелёных тестов, обновления
документации, commit/push в отдельную feature-ветку, открытого Pull Request в
`main` и финального ревью PR. Полный выпуск завершается только после merge и
разрешённого пользователем deploy с post-deploy проверкой.

Агент может самостоятельно создавать feature-ветку `codex/<feature-slug>`,
делать commit, push и открывать Pull Request в `main`. Прямой push в `main`
запрещён. Агент не выполняет merge PR без отдельного явного разрешения
пользователя. Разрешение на merge не является разрешением на production deploy:
непосредственно перед deploy агент обязан остановиться, назвать подготовленный
commit SHA и запросить новое явное разрешение. Разрешение нельзя предполагать из
исходной постановки задачи или предыдущего merge/deploy.

До deploy агент может подключаться к production по SSH для сбора диагностических
данных. Хост бери только из `ansible/inventory/production.ini`; не дублируй IP в
командах или документации. Диагностика по умолчанию read-only и не разрешает
ручное изменение production.

## Scope Contract и границы ответственности

До запуска проектных ролей главный агент фиксирует Scope Contract:

- `scope_revision`, цель и пользовательский сценарий;
- утверждённые требования и критерии приёмки;
- явные non-goals;
- разрешённые компоненты и ожидаемые файлы;
- существенные ограничения и бюджет изменения;
- для каждой партии — ID пунктов плана, владение файлами и запрещённая работа.

Scope Contract и остальные рабочие материалы фичи хранятся только в
`.codex/work/<feature-slug>/`. Этот каталог игнорируется Git: его содержимое
служит временной координацией агентов, не входит в commit или Pull Request и не
является постоянной документацией продукта.

Для продуктового изменения пользователь утверждает наблюдаемое поведение,
требования и non-goals. Главный агент самостоятельно выбирает технические детали
только внутри этих границ. Новое пользовательское поведение, обязательный edge
case, компонент, контракт или расширение non-goals требует нового явного
подтверждения пользователя. Технический бюджет или ожидаемые файлы главный агент
может уточнить сам, только если цель, поведение и границы компонентов не меняются.
Каждая `scope_revision` неизменяема. После любого разрешённого уточнения главный
агент повышает revision и заново передаёт Scope Contract всем затронутым ролям;
работа по устаревшей revision запрещена.

Каждая передача между ролями содержит актуальную `scope_revision`, назначенные
BR/AC и пункты плана, разрешённые файлы, non-goals и критерий завершения. Агент
не выполняет соседнюю работу «заодно» и не превращает риск, идею или рекомендацию
в новое требование. Если работа требует выхода за Scope Contract, агент
останавливается до изменений и возвращает `scope_change_request`: причину,
трассировку к исходной задаче, минимальное расширение и влияние на бюджет.
Главный агент либо отклоняет запрос, либо согласует техническое уточнение внутри
scope, либо останавливает затронутую работу и запрашивает решение пользователя.

Reviewer не является постановщиком задач. Каждая находка получает один тип:

- `blocking_in_scope` — нарушение утверждённого BR/AC, non-goal или пункта плана,
  либо регрессия, внесённая проверяемым diff;
- `scope_change_request` — новое поведение, компонент, обязательный edge case
  или hardening за пределами Scope Contract;
- `follow_up` — необязательное улучшение, не требуемое текущей задачей.

Вердикт `changes_requested` допустим только при наличии хотя бы одного
`blocking_in_scope` с прямой трассировкой к Scope Contract или регрессии из diff.
Остальные находки не передаются implementer-у как обязательные задачи. Главный
агент проверяет эту классификацию до выдачи исправлений и отклоняет
out-of-scope изменения даже при зелёных тестах.

## Адаптивная продуктовая команда

Для продуктовых изменений главный агент оркестрирует проектные роли из
`.codex/agents/`. Роли запускаются адаптивно, а не формальным полным конвейером:

- небольшая локальная фича: `product-agent` → облегчённый `plan-maker` →
  `plan-implementer` → batch `code-reviewer` → `product-reviewer` → Pull Request
  → финальный `code-reviewer`;
- обычная фича: `product-agent` → `product-architect` → `plan-maker` →
  архитектурное ревью плана → реализация → batch-ревью → `product-reviewer` →
  Pull Request → финальное интеграционное ревью;
- крупная фича использует полный маршрут и несколько независимых пар
  implementer/reviewer.

Чисто техническое обслуживание без изменения пользовательского поведения или
бизнес-правил может не использовать продуктовые роли. Архитектора также можно
не запускать, когда изменение не затрагивает контракты, модели, взаимодействия
компонентов или существенные нефункциональные требования. В таком случае главный
агент фиксирует, что архитектурное изменение не требуется, и сам ревьюит и
утверждает облегчённый план до запуска implementer-а.

Временные артефакты фичи хранятся в `.codex/work/<feature-slug>/`: `business.md`,
при необходимости `architecture.md`, `plan.md` и `acceptance.md`. Следующая
стадия не начинается, пока предыдущий обязательный артефакт не утверждён.
Существенные продуктовые неопределённости подтверждает пользователь; агенты не
заполняют их догадками.

Рабочие документы должны быть короткими: не копируй в них большие фрагменты
production-кода, полные логи проверок, хэши рабочего дерева, закрытые revision
или task packets, уже переданные роли. План фиксирует результат, владение
файлами, RED/GREEN-команды и критерий завершения; task packet передаётся роли
непосредственно при запуске.

Один `plan-implementer` получает не более двух пунктов плана. Параллельная
реализация разрешена только для партий без незавершённых зависимостей и
пересекающихся файлов. Каждую партию до публикации проверяет отдельный `code-reviewer`.
После объединения партий и продуктовой приёмки главный агент публикует
feature-ветку и открывает Pull Request в `main`, а новый экземпляр `code-reviewer`
проводит финальное интеграционное ревью точного PR head SHA через GitHub CLI.
Перед публикацией главный агент переносит из временных артефактов в описание PR
короткий Review Brief: цель, наблюдаемое поведение, non-goals, критерии приёмки,
проверки, риски и deploy impact. Финальный reviewer использует Review Brief,
канонические документы, diff и checks; `.codex/work/` он не читает.
Reviewer не исправляет собственные замечания: изменения возвращаются
исходному implementer-у, после push исправлений запускается новый reviewer.
Implementer получает только подтверждённые главным агентом
`blocking_in_scope`; `scope_change_request` и `follow_up` не входят в fix batch.

`sandbox_mode = "read-only"` в конфигурации reviewer-а задаёт безопасный default,
но live runtime permissions родительского потока могут его переопределить. Где
поверхность это поддерживает, главный агент запускает reviewer с read-only
permissions. Главный агент не запускает reviewer параллельно с write-сессиями:
он дожидается завершения всех изменяющих файлы агентов и сам не меняет рабочее
дерево до окончания ревью. Затем он сравнивает `git status --short` и diff до и
после ревью и отклоняет результат reviewer-а, если рабочее дерево было изменено.
При финальном PR review разрешено единственное внешнее изменение: публикация
структурированного review-комментария через `gh pr review --comment`. Reviewer не
выполняет push, merge, close или edit PR. Поскольку автор PR не может одобрить
собственный PR тем же GitHub-пользователем, вердикт `approved` либо
`changes_requested` фиксируется в тексте комментария и проверяется оркестратором.

Главный агент отвечает за распределение партий, разрешение конфликтов,
интеграцию, полный `make test`, итоговый diff, документацию, feature-ветку,
commit/push, создание Pull Request и release gates из
`docs/DEVELOPMENT_WORKFLOW.md`. При завершении работы он оставляет PR открытым и
возвращает пользователю его URL, проверенный head SHA и результаты checks. Ни
один дочерний агент не выполняет merge PR или production deploy.

## Команды

Команды Django выполняются из `src/`. Тесты запускаются из корня:

```bash
make test
make test ARGS="apps.users.tests.test_first_free_link"
make test ARGS="apps.users.tests.test_first_free_link.TestFirstFreeLink.test_first_free_link_30days"
```

Локальный стек:

```bash
docker compose -f docker-compose.local.yml up -d
```

Production разворачивается только по `docs/DEPLOY.md`, через Ansible и после
явного разрешения пользователя. Не используй `docker compose up` как локальную
замену release-процессу.

## Правила реализации

- Пиши тесты до production-кода (TDD), используя существующий `pytest` или
  `unittest`; новый test framework не добавляй.
- Сервисы — `@final` frozen dataclass с `kw_only=True`, `slots=True` и
  `frozen=True`, реализующий `__call__` с keyword-only аргументами.
- Зависимости сервисов инъектируй через поля dataclass. Создание зависимых
  сервисов внутри `__call__` запрещено; wiring выполняют module-level factory
  functions.
- ORM-запросы переиспользуй или добавляй в `selectors.py`, не размещай их в
  сервисах.
- Доменные исключения хранятся в `exceptions.py`, enum — в `enums.py`; между
  слоями передавай DTO.
- Используй `from __future__ import annotations`. Импорты только для аннотаций
  помещай под `TYPE_CHECKING`.
- Каждый пакет явно реэкспортирует public symbols из `__init__.py`; star imports
  запрещены.
- Новые модели наследуй от `BaseDjangoModel`. Не дублируй `is_active`,
  `created_at`, `updated_at`; используй `Model.objects.active()` вместо
  `filter(is_active=True)`.
- `BaseServiceError` и `BaseInfraError` принимают `telegram_id` первым
  аргументом; docstring исключения является сообщением пользователю.
- API-тесты передают заголовок `Bot-Auth-Token`. Внешние VDS HTTP-вызовы мокай
  через `responses`, Telegram-вызовы — патчем `apps.core.bot.TelegramBot`.
- При изменении бизнес-логики, контрактов, моделей или архитектуры обновляй
  соответствующие docstrings и документы в `docs/`.
- `apps/music/` — статическая FakeTLS-заглушка. Не изучай, не рефактори и не
  изменяй её без прямого запроса пользователя.

## Архитектурные инварианты

- База данных — source of truth для MTProto-ключей; VDS — равноправные зеркала.
- Issue/reissue выполняет только DB write. Распространение ключа на все healthy
  VDS делает асинхронная reconcile-задача.
- Один `MTPRotoKey` содержит один secret для всей fleet; серверные ссылки
  формируются на лету.
- Кнопка `NotificationTemplate` содержит либо URL, либо callback; URL имеет
  приоритет, а для callback должен существовать aiogram handler.

Детали и актуальные бизнес-правила не дублируй здесь — поддерживай их в `docs/`.
